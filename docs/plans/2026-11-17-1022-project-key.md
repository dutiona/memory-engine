# feat(scope): file memory under a machine-independent project key (#1022)

## Outcome

Each MCP request's five `ME-Project-*` headers are decoded once, canonically, with userinfo stripped before anything
holds a remote, and key rules version 1 turn them into a remote key, a `<machine>:<path>` key, or no key. The decoder
and the derivation take only a header map and the authenticated machine, so #1025's lifecycle routes call them
unchanged. `remember(content, level?)` files into the session's project (no key: the machine's `unscoped` bucket), and
into `user` only when asked; its receipt names the Home, plus one `set_level` hint line when the placement looks
doubtful. `recall` reads exactly the session's project (only `user` while that project holds nothing) and `user`;
another project only through `project`. `set_level(id, level)` moves one of the session's own memories between its
project (or bucket) and `user`, in one storage transaction with its call record. Every call record keeps the decoded
facts, the dropped-fact flags, the key and the rules version, filed under the calling machine's bucket, and no read
creates a project. Until #1028's `headersHelper` sends the facts, real sessions stay keyless; the proof here is the
HTTP-level suite.

## Decisions (defaulted; the three marked * need Michaël's call at plan approval)

- **D1 record Home.** A call record is filed under the calling machine's bucket, with one exception: a valid
  `remember`'s record is filed under the Home it writes to. Every record is a scoped write that creates its scope path
  in its own transaction (`MemoryEngine::ingest_at`, or `move_fact` for `set_level`'s, item 3), so a project node
  exists only with an event or a memory filed under it, which is ADR-0020 §8's "known once an event or a memory was
  filed under it", and a failed record leaves no node. A record is provenance, and filing a `recall`'s or a refusal's under a project would let a
  read make that project known. A fact write that fails after `remember`'s record leaves a project that is known by
  that definition. `set_level`'s record is filed under the bucket, which its move creates when absent, with the target
  node, in the move's own transaction. Re-filing reads the payload, never the record's scope.
- **D2\* what mints.** `remember` at project level and `set_level(id, "project")` create the session's project node;
  `recall`, refusals and records never do. A rehomed or renamed project has nothing filed by construction, so refusing
  would block the owner's rehoming case. This amends ADR-0021 §8's list (item 7). If declined: item 8 answers
  `error: project <key> holds no memory yet; remember one there first`, and item 7 is dropped.
- **D3\* receipts.** ADR-0020 §8 "the same receipt as `remember`" is read literally: a move answers `stored <id> in
  <home>, visible to all agents`; an unchanged level answers `unchanged: <id> is already in <home>, visible to all
  agents`. Alternative: `moved <id> to <home>, ...`.
- **D4\* expired facts.** A fact that is not live now (`t_expired` set, or `t_invalid` at or before the call's time) is
  `not found` to `set_level`: it is no memory `recall` returns, and #1023's forget ends validity. A future `t_invalid`
  is live, exactly as the reads judge it. `owned_fact` leaves liveness to each tool so #1023 can answer
  `already forgotten`.
- **D5 no registry crate yet.** `me-project-registry` belongs to ADR-0021 stage 1; the derive half of `project.rs`
  imports only `std`, `crate::auth::Machine` and `memory_engine::types::MAX_SEGMENT_LEN`, so stage 1 moves it with
  one import swapped (the registry crate depends on no memory crate).
- **D6 over-long key.** Past 256 bytes the final key is rejected with no fall-through to `origin` (ADR-0021 §8: "a
  final key").
- **D7 userinfo.** The server applies the plugin's scheme rule, then its scp rule to the result, so it removes at least
  everything the plugin removes, plus the `token@` of `token@host:a://b`, which the plugin keeps (git cannot use such
  a remote, so no issue is filed).
- **D8 `MemoryOp` stays at revision 1.** Its payload only gains keys; a record without `project` predates #1022 and has
  no Capture context, which ADR-0021 §12 lists for review and never re-files.
- Out, each owned elsewhere: C21's alias hint and the confirmed `add` (stage 4; a hint naming a missing operation
  misleads); C33's `${PROJECT_ROOT}` hint and the path hints (stage 3); the user-level episodic hint (#1025, where
  episodic memories first exist); C34 (stage 1); the cross-channel proof (#1028).

Accepted residuals: a dev root configured through a symlink gives remote-less projects no
path key, since git reports resolved paths (fails closed into the bucket; documented, and raised as a follow-up
for #1028: the client resolves the configured dev root with `pwd -P` before sending it); bucket memories written before
#1028 stay in their bucket (documented: a keyless session raises one to `user`, a project session brings it down).

## Key rules, version 1 (normative for items 1 and 2)

Decoding, per header (`ME-Project-Root` root, `-Dev-Root` dev_root, `-Upstream-Url` upstream_url, `-Origin-Url`
origin_url, `-Branch` branch); the first failing rule drops the fact and records its `Flaw`:

1. No header: no fact, no flag.
2. Two or more headers of that name: `repeated`.
3. Empty value: `empty`.
4. Over 4,096 bytes: `too_long`.
5. A byte outside 0x21 to 0x7E: `raw_byte`.
6. Dev root only: not starting with `/`, or holding `%`, `"` or `\`: `not_plain_absolute`; otherwise taken as sent,
   never decoded.
7. A `%` not followed by two hex digits: `bad_escape`; each `%HH`, either case, decodes exactly once to its byte.
8. Not UTF-8: `not_utf8`.
9. Any `char::is_control` character (C0, DEL, C1): `control`.
10. Both URLs then lose their userinfo (D7), in two steps: when `://` occurs, the authority after its first occurrence
    (up to the next `/`) loses everything through its last `@`; then, when a `:` exists and the text before the first
    one holds no `/`, that text loses everything through its last `@`.

Remote key, tried on `upstream_url` then `origin_url`; a URL that gives none is ignored as input:

- R1. A `file:` prefix in any case, or a remote-helper prefix `[A-Za-z][A-Za-z0-9+.-]*::`: none.
- R2. Scheme form (`[A-Za-z][A-Za-z0-9+.-]*://`): the authority runs to the first `/`; the host is the authority after
  its last `@`; a host starting with `[` runs through the first `]` (no `]`: none); otherwise it ends at its first `:`.
  After the host only nothing, or `:` and zero or more ASCII digits (the port, dropped), may follow; else none.
- R3. scp form: a `:` exists and the text before the first one holds no `/`. The host starts after the last `@` before
  it, bracket-aware (`[...]` must be followed by `:`); the path follows the `:` that ends the host.
- R4. Anything else is a local path: none.
- R5. Path: trim `/` at both ends, drop one trailing `.git` (lowercase only: `.GIT` stays), trim trailing `/` again.
  Empty host or path: none.
- R6. Key: the host lowercased in ASCII only, `/`, the path with its case kept. No URL-level decoding.

Path key, when no remote gives one; it needs both the root and the dev root:

- P1. Trim trailing `/` from the dev root (`/` becomes empty); the root must start with it followed by `/`.
- P2. The rest, trailing `/` trimmed, is the relative path; empty (the root is the dev root): none.
- P3. A segment that is empty, `.` or `..`: none.
- P4. Key: `<machine>:<relative path>`.

Final key: the first candidate in that order, kept only when `project:<label>` fits 256 bytes (D6). Label: every byte
outside `A-Z a-z 0-9 - . _ ~` as uppercase `%HH` (unchanged from `home.rs`).
