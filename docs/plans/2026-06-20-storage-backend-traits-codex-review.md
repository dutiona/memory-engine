**Findings**
- [BLOCKER] In [D1 / P1](</home/mroynard/dev/memory-engine/.worktrees/feat-629-storage-traits/docs/plans/2026-06-20-storage-backend-traits.md:34>), the `for_each_X(&mut dyn FnMut(...) + Send)` shape itself is acceptable, but the object-safety proof is not. With default `#[async_trait]`, `&self` async methods are rewritten to `Future + Send` with a hidden `Self: Sync` bound (docs: https://docs.rs/async-trait/latest/async_trait/). The proposed `_assert_obj_safe(_: &dyn StorageBackend)` / `Arc<dyn StorageBackend>` coercion only proves vtable creation, not that async methods are callable through the intended object type. The existing codebase consistently uses shared trait objects as `Send + Sync` in async paths, e.g. [src/async_engine.rs](/home/mroynard/dev/memory-engine/.worktrees/feat-629-storage-traits/src/async_engine.rs:182). I would treat this as blocking until the storage traits themselves carry `Send + Sync` and P1 includes an actual awaited call through the trait object.
- [BLOCKER] The [SearchIndex section](</home/mroynard/dev/memory-engine/.worktrees/feat-629-storage-traits/docs/plans/2026-06-20-storage-backend-traits.md:133>) is not faithful to the current contract because it returns bare `Vec<i64>`. Current search behavior exposes scores end-to-end: `SearchResult` has a public `score` field [src/search/hybrid.rs](/home/mroynard/dev/memory-engine/.worktrees/feat-629-storage-traits/src/search/hybrid.rs:50), FTS-only/vector-only modes preserve backend scores [src/search/hybrid.rs](/home/mroynard/dev/memory-engine/.worktrees/feat-629-storage-traits/src/search/hybrid.rs:191), and both CLI and MCP surface them [memory-engine-cli/src/commands/query.rs](/home/mroynard/dev/memory-engine/.worktrees/feat-629-storage-traits/memory-engine-cli/src/commands/query.rs:113), [memory-engine-mcp/src/depth.rs](/home/mroynard/dev/memory-engine/.worktrees/feat-629-storage-traits/memory-engine-mcp/src/depth.rs:96). Freezing `Vec<i64>` here forces a later trait reshape or a user-visible behavior change.
