# Adversarial Review — DreamCycle R7/R8 + Default DBSCAN Impl (#49)

**Reviewer lens:** bi-temporal data semantics, storage/schema claims, API/design soundness.
**Plan under review:** `docs/plans/2026-06-16-dreamcycle-r7r8-default-impl.md`
**Repo state:** worktree `feat-49-dreamcycle-default`, schema v11.
**Verdict:** The transactional-delta core and the no-migration claim are sound and well-grounded. Two design decisions (Supersede-via-lineage, and the TagOutcome lock path) have concrete BLOCKER/HIGH defects. Quarantine semantics are correct on the retrieval axis but **not auditable** as specified. Idempotency and non-atomicity have real gaps the plan under-states.

Severity legend: **[BLOCKER]** ship-stopper · **[HIGH]** must fix before merge · **[MEDIUM]** fix or explicitly accept · **[LOW]** nit / doc.

---

## 1. Quarantine semantics (D6)

**The axis choice is correct.** Quarantine means "remove from retrieval now, keep for mining." That is exactly system-time retirement (`t_expired`), not valid-time invalidation (`t_invalid`). Setting `t_invalid` would assert a real-world claim ("this stopped being true") that quarantine does not make — a corrected fact may still be *valid in the world*; the agent simply must stop surfacing it. D6 gets the temporal axis right, and the doc (`bi-temporal-semantics.md:96-106`) backs this: conflict resolution sets **both** `t_expired`+`t_invalid`; forgetting sets only `t_expired`. Quarantine belongs with the latter family. **Sound.**

**Exclusion from ALL retrieval — verified true, but the "graph" leg is vacuous.**
- FTS5: `fts.rs:43` — `AND f.t_expired IS NULL` pushed into SQL. ✅
- Vector brute-force: `vector.rs:61` — `WHERE t_expired IS NULL`. ✅
- HNSW (`ann` feature): two independent guards — `notify_expire` tombstones the vector (`ann.rs:345-350`) **and** `check_fact_filters` re-checks `t_expired IS NULL` in SQL at search time (`ann.rs:367`). So even if the post-commit `notify_expire` is skipped/lost, the SQL filter still excludes the row. ✅ (belt-and-suspenders)
- "Graph": **the engine `query()` path has no graph-traversal stage.** `engine/query.rs:82` delegates solely to `hybrid_search` (FTS5 + vector + RRF, `hybrid.rs:144`); grep for `graph`/`edge` in `hybrid.rs`/`query.rs` returns nothing. `resume_context` (`resume.rs`) composes `list_pinned`/`list_by_importance_score`/`list_due`/`list_by_scopes_recent`, all `t_expired IS NULL`. The graph is used only for `explain_fact` context and is not a retrieval source. So `t_expired` does exclude from every *real* retrieval surface — but the plan (and CLAUDE.md's "hybrid FTS5 + vector + graph") implies a graph retrieval leg that does not exist.

  **[LOW]** Task 1(b) and Task 10 assert "absent from `query`". True, but the spike/integration test should *also* assert absence from `resume_context` and (under `--all-features`) from the HNSW path after dropping the `notify_expire` — that is the leg most likely to regress, and Task 10 only runs the default feature set unless `cargo test --all-features` exercises it. Make the HNSW-quarantine exclusion an explicit `--all-features` integration assertion, not an implied one.

**The row survives and stays get-able — verified.** `expire()` only sets `t_expired` (`facts.rs:330-340`); `get()` has no `t_expired` filter (`facts.rs:203-214`). A quarantined fact is `get`-able and `list_all`-able. ✅

**[HIGH] — Quarantine is indistinguishable from Ebbinghaus-forgotten in the audit trail.** This is the real defect in D6, and the plan does not surface it.
- The metadata marker `{"quarantine":{"reason","at"}}` is the *only* thing separating a quarantined fact from a forgotten one — both set `t_expired` and nothing else.
- But the inspection path that classifies expiry, `determine_state` (`inspect/explain.rs:91-96`), reads **only `fact.t_expired.is_some()`** and returns `ExpiredReason::Unknown`. It never inspects `metadata`. So `explain_fact` on a quarantined fact reports `Unknown`, identical to a forgotten fact (`inspect/types.rs:42-53` documents that forgetting/dedup/conflict all currently collapse to `Unknown`).
- `hybrid.rs:65-71` already calls this out as a known limitation: "`t_expired` is a generic tombstone... consumers wanting true decay-only counts should cross-reference `ExpiredReason`." Quarantine *adds a fifth indistinguishable tombstone* without extending `ExpiredReason`.
- **Consequence for the stated goal ("keep for audit/mining"):** mining works (you can scan `metadata` for the marker), but *auditing* via the inspection API does not — `explain_fact` cannot tell you a fact was quarantined. The marker is sufficient for a Rust-side `WHERE json_extract(metadata,'$.quarantine') IS NOT NULL` scan; it is **not** sufficient for the inspection surface the crate already ships.
- **Fix (recommend):** add `ExpiredReason::Quarantined { reason: String }` and teach `determine_state` (or a metadata-aware variant) to read the marker. This is a `#[non_exhaustive]`-friendly enum extension (the variant set is not `#[non_exhaustive]` today — check `inspect/types.rs:47`; adding a variant is a breaking change to that enum unless it gains `#[non_exhaustive]`). At minimum, the plan must *state* the audit-blindness as a limitation rather than claiming the marker is enough.

**[MEDIUM] — Conflation risk with conflict resolution on the inverse axis.** `bi-temporal-semantics.md:96-106` reserves `t_expired`+`t_invalid` (both set) for conflict-driven invalidation. Quarantine sets only `t_expired` — good, it won't be misread as a conflict. But the *correction* case D9(e) handles ("don't/stop/no" → quarantine the corrected fact) is **semantically a conflict** (a new fact contradicts an old one). Modeling it as quarantine (system-time only) loses the valid-time signal that the corrected fact *stopped being true in the world*. If the corrected fact had a `t_valid` window, leaving `t_invalid` unset means a later historical query (`valid_at` in the past, `list_active_at`) will still treat it as world-valid. **Decide explicitly:** is a user correction a "stop showing this" (quarantine, t_expired only) or a "this became false" (conflict, both)? The plan picks the former by fiat; for user corrections the latter is arguably correct. Flag for the maintainer.

## 2. Supersede (D-note / Task 2, 5, 9)

**[BLOCKER] — `LineageStore` is the wrong structure for Supersede, and reusing it will violate a UNIQUE constraint.**

The plan models `Supersede{old_id, new_id}` → `expire(old) + LineageStore::insert(new ← [old])` (plan lines 53, 62). Three concrete problems, each independently sufficient to break it:

1. **UNIQUE(wisdom_fact_id) collision.** `lineage` has `CREATE UNIQUE INDEX idx_lineage_wisdom_fact_id ON lineage(wisdom_fact_id)` (schema.rs:855, confirmed in snapshot line 75). The `new_id` in a Supersede is, in the DBSCAN flow (Task 9d), produced by a `Promote` delta — and `Promote` *already* inserts a lineage row keyed on that same `new_id` via `promote_in_conn`→`LineageStore::insert` (`cognitive.rs:220`). A subsequent `Supersede{old, new}` inserting a *second* lineage row for the same `wisdom_fact_id` hits the UNIQUE index and the whole `apply_cycle_report` transaction rolls back. The plan's own Task 9d ("emit `Promote`/`Supersede` deltas for clusters") makes the Promote-then-Supersede-on-the-same-id sequence the *expected* path, so this is not a corner case.

2. **`provenance` is NOT NULL CHECK(json_valid).** `lineage.provenance TEXT NOT NULL CHECK(json_valid(provenance))` (schema.rs:852). `LineageStore::insert` takes a `&PromotionProvenance` and serializes it (`lineage.rs:34,58`). A Supersede has no natural `PromotionProvenance` — it is not a promotion. The plan would have to synthesize a fake provenance envelope, polluting the lineage table's semantics (lineage = "wisdom synthesized from sources", not "fact replaced fact").

3. **Direction/semantics mismatch.** Lineage means *new wisdom was derived from N source facts*. Supersede means *fact B replaces fact A* (a 1:1 temporal-succession edge). Overloading lineage to also mean succession makes `get_source_fact_ids`/`explain_fact` lineage queries ambiguous: is `old_id` a *source* of `new_id`, or its *predecessor*? These are different relations.

**The right structure is a graph edge.** Crucially, `relation_type` is a **free-form `String`**, not an enum (`types.rs:186,372`; `edges.rs:44` inserts it directly). So a `"supersedes"` edge needs **zero schema change** — `EdgeStore::insert(EdgeRecord{ source_fact_id: new_id, target_fact_id: old_id, relation_type: "supersedes", ... })`. The plan's premise that "lineage is the right structure vs a graph EdgeType" is backwards: the EdgeType path is *cheaper* (free-form string, no UNIQUE conflict, no fake provenance) *and* semantically correct (edges already carry `t_created`/`t_expired` for temporal succession). **Recommend: model Supersede as a `"supersedes"` edge, not a lineage row.** If lineage is desired for the *promotion* that produced `new_id`, that is a separate `Promote` delta and stays in lineage — cleanly separated.

**[HIGH] — Forward-reference resolution in `validate_report` is under-specified and has an ordering hazard.** Task 5 says: "`Supersede` `old_id` exists + `new_id` exists-or-introduced-earlier-in-vec." The validator runs **read-only on a single read connection** (Task 5, "single read connection") *before* any AddFact has been inserted. So `new_id` for an `AddFact`-introduced fact does not exist in the DB yet at validate time — the validator must track a *synthetic* id set built from `AddFact` deltas seen earlier in the vec. But `AddFact` produces a DB-assigned `last_insert_rowid()` only at *apply* time (`facts.rs:109`); at *validate* time there is no id to forward-reference. The `Supersede{old_id, new_id}` delta therefore cannot name a not-yet-inserted AddFact by a real `FactId` — the `new_id` field is an `i64` (Task 2), but the AddFact'd fact has no id until applied. **The plan conflates two id spaces** (pre-assigned DB ids vs. within-report symbolic references). Either: (a) `CycleDelta::AddFact` must carry a *symbolic* local handle that `Supersede`/`Promote` reference, resolved to real ids during apply; or (b) forbid forward-referencing an AddFact from a Supersede in v1 (Supersede may only target pre-existing DB facts) and delete the "introduced-earlier-in-vec" clause. Task 5 test (f) ("Supersede forward-ref: AddFact then Supersede to that new id") asserts behavior the type system as specified **cannot express**. Resolve the id-space design before Task 2 freezes the wire format (it is serde-locked in Task 2's round-trip test).

## 3. The no-migration claim (D7)

**Largely correct — better than the plan even argues.**

- `facts.metadata` is a free-form JSON column: `metadata TEXT NOT NULL DEFAULT '{}' CHECK(json_valid(metadata))` (schema.rs:798, snapshot line 102). A new top-level key is a value change, not a DDL change. ✅
- **No index on metadata** (grep of `INDEXES_DDL` schema.rs:937-956: none reference `metadata`). So no index is perturbed by a new key. ✅
- **Schema snapshot is pure DDL.** `schema_v11.snap` captures `CREATE` statements from `sqlite_master` (the file is all `-- table:`/`-- index:`/`-- trigger:` DDL, lines 5-142), *not* table data. A new row in `config` (the watermark) does **not** appear in this snapshot. The test is `schema_v11_snapshot` at `schema.rs:2200`, asserting snapshot name `"schema_v11"` (`schema.rs:2204`). The plan's verification command `cargo test schema_v11_snapshot` (plan line 113) matches the fn name. ✅
- **Dump snapshots also unaffected — but for a reason the plan should note.** `inspect/dump.rs:69-71` *does* serialize `list_config(conn)` into the engine dump, so a naive expectation is that a new config key breaks the populated-dump snapshot. It does not, because **both** dump snapshots redact config: `snapshot_empty_engine_dump` uses `".config" => insta::sorted_redaction()` (dump.rs:486) and `snapshot_populated_engine_dump` uses `".config" => "{}"` (dump.rs:522). So new config keys are masked. ✅ **[LOW]** This is also a blind spot: the dump-snapshot tests cannot catch a regression in *which* config keys are written. If watermark correctness matters, add a direct `get_config(conn,"last_dream_cycle_at")` assertion in Task 7 rather than relying on any snapshot.
- **`last_consolidated_at` precedent is real.** `consolidation/mod.rs:76` reads it via `get_config`, `mod.rs:101` writes via `set_config`. The dream-cycle watermark mirrors this exactly. ✅ D7 is well-grounded.

**[MEDIUM] — `json_valid(metadata)` CHECK + `merge_metadata` (Task 4).** The CHECK constraint (`schema.rs:798`) means `merge_metadata` must emit valid JSON or the UPDATE fails. Task 4 says "shallow-merge object via `json_set`, reject non-object patch." Two cautions: (1) SQLite's `json_set` on a column whose current value is a JSON *scalar* (not object) — e.g. a fact whose metadata was somehow set to `"foo"` or `42` — behaves surprisingly (`json_set('42','$.k','v')` errors or no-ops depending on build). The existing code already normalizes non-object metadata to `{}` in the promote path (`cognitive.rs:163-166`), so there is precedent the plan should reuse: normalize-then-merge, don't assume the existing value is an object. (2) Concurrency: `merge_metadata` is read-current-then-write (Task 4), non-atomic across the read and the write unless done inside the apply transaction. Since `apply_cycle_report` holds the single write lock for the whole replay (Task 5), this is safe *inside* apply — but `merge_metadata` as a standalone `pub(crate)` helper invoked elsewhere on a bare connection would have the same TOCTOU as the documented `insert_or_reinforce` caveat (`facts.rs:135-137`). Document that `merge_metadata` is only safe under the write lock.

## 4. Idempotency (Task 10)

The plan claims a double-fired daily cycle is "near-noop" via watermark + metadata marker. **Partially true; the plan over-states it.** Concrete gaps:

**[MEDIUM] — Facts created during the cycle window are silently dropped from the *next* window, not re-picked.** The window is `[last_dream_cycle_at, now)` (Task 7). `apply_cycle_report` advances `last_dream_cycle_at` to (presumably) the cycle's `now`. But `consolidate()` runs *first* and in its own transaction (D7 note), and `run_dream_cycle`→produce→review→apply spans wall-clock time. Any fact ingested between the producer's window-`now` and the apply's watermark-write falls into a gap: it is `> last_dream_cycle_at` of the *previous* run but `< last_dream_cycle_at` written by *this* run, so it is never in any window. This is the same class of bug `consolidate()` explicitly guards against — it only advances the watermark "if dedup actually ran" and notes "facts ingested during the over-cap period must be retried on the next run" (`consolidation/mod.rs:98-102`). The plan inherits none of that care. **Fix:** the watermark written by apply must equal the producer's window upper bound (`time_window.end`), not a fresh `Utc::now()` taken at apply time. Capture the boundary once, in `CycleMetadata.time_window`, and write *that*.

**[MEDIUM] — Double-fire is not a no-op if the two fires straddle the first's apply.** "Re-run → second cycle selects ~0" (Task 10) holds only if the first cycle's `apply` (which advances the watermark + marks `processed_ids`) committed before the second `run` reads the watermark. If two daily cycles fire concurrently (the "double-fired" scenario), both read the *same* old `last_dream_cycle_at`, both select the *same* window, both produce overlapping deltas. The metadata marker (`mark_dream_cycled`) only filters facts marked by an *already-committed* cycle; concurrent producers see unmarked facts. Result: double promotion / double rescoring (importance moved `±2` twice → `±4`, violating the D1 "±2/cycle" invariant). The single write lock serializes the two *applies*, but not the two *produces*. **The watermark + marker make sequential re-runs idempotent; they do NOT make concurrent double-fires idempotent.** State this honestly, or gate `run_dream_cycle` behind a "cycle in progress" config flag.

**[LOW] — Clock skew.** Watermark comparison is RFC-3339 string/`DateTime` (`consolidation/mod.rs:77`). On a single host this is fine. If `now` is ever taken from a different clock than the stored watermark (multi-node, NTP step-back), `time_window.start > time_window.end` is possible → `list_active_in_period(start,end)` with `start>end` yields the SQL predicate `t_valid < end AND t_invalid > start` which silently returns near-empty, not an error (`facts.rs:768-772`). Add a `start <= end` assertion when building `CycleContext.time_window`.

**[LOW] — `AdjustScore` idempotency under marker.** Rescoring (`AdjustScore`) is applied to facts in the window; the marker excludes already-dreamt facts from the *next* window's *selection*. Good. But a fact can legitimately re-enter a window (new outcomes recorded after it was dreamt). The plan's selection helper `list_undreamt_in_period` (Task 4) excludes *any* marked fact forever, so a fact that accrues new negative outcomes after its first dream cycle will **never be re-rescored**. Is "dream once, never again" intended? For `Promote` yes; for outcome-driven `AdjustScore` almost certainly no. The single boolean marker conflates "I have processed this fact's *promotion* candidacy" with "I have processed this fact's *current* outcome signal." Consider a per-fact `last_dream_cycle_id` (monotonic, Task 7 already mints `dream_cycle_next_id`) so re-selection can be "marker cycle < current − N", not "marker present."

## 5. Non-atomic cycle (D7 note)

**[HIGH] — The failure window is wider and more corrupting than the plan admits, and the plan offers no recovery story.**

The plan states (limitation #2): `consolidate()` commits before `apply_cycle_report`'s savepoint; "a single-transaction cycle is #578." That correctly identifies the seam but mis-sizes the blast radius:

- **`consolidate()` mutates the corpus the producer already read.** The 3-pass consolidate **expires near-duplicate facts** (dedup pass, `consolidation/mod.rs:87` → `local_dedup` sets `t_expired`) and rebuilds cluster/global summaries. In the DBSCAN flow (Task 9), the producer runs `consolidate` (step b) *then* clusters (step c) *then* emits deltas referencing fact ids (step d). If the process dies **after `consolidate` commits but before `apply` commits**, the corpus has been deduped/re-summarized but **none** of the cycle's promotions/rescorings/quarantines landed, and the watermark was **not** advanced. On restart, the next cycle re-reads `[same last_dream_cycle_at, new now)` — it will re-consolidate (idempotent: dedup re-runs, cluster summaries are `delete_by_level`+rebuild, `cluster.rs:58`) and re-produce. **So consolidate is replay-safe and the cycle is recoverable** — but only because consolidate happens to be idempotent, a property the plan does not assert or test.

- **The real corruption risk is partial apply *within* `apply_cycle_report`.** Task 5 wraps the whole replay in one `unchecked_transaction()`/savepoint and asserts full rollback on any invalid delta (test c). Good — *if* the failure is a delta error. But the plan also does **post-commit HNSW notify** outside the transaction (Task 5: "commit; drop lock; post-commit HNSW notify"). If the process dies *after commit but before the HNSW notifies fire*, the SQLite state is correct (facts promoted/quarantined) but the in-memory HNSW index is **stale**: quarantined facts not tombstoned (still vector-searchable until the SQL `check_fact_filters` catches them — which it does, `ann.rs:367`, so this is *masked* for quarantine) and promoted facts not inserted (so a freshly-promoted wisdom fact is **invisible to vector search** until the index is rebuilt). This is the same post-commit-notify pattern as `promote_with_lineage` (`cognitive.rs:224-230`), so it is not a *new* risk — but applying a *batch* of deltas multiplies the count of possibly-un-notified facts. The plan should note HNSW rebuild-on-open is the recovery, and confirm it exists.

- **Recommendation:** State the recovery contract explicitly in D7: (1) consolidate is idempotent → safe to replay; (2) apply is atomic in SQLite → no partial DB state; (3) HNSW is reconstructed from SQLite on open → post-commit notify loss self-heals on restart. If any of these three is not actually true (esp. #3 — verify HNSW rebuilds from the `t_expired IS NULL` set on open), the "acceptable / recoverable on next run" claim is unsupported. As written the plan *asserts* recoverability without establishing these three legs.

## 6. Decision soundness

**D2 (`Vec<CycleMetadata>` vs issue's `Vec<CycleReport>`) — [MEDIUM], correctly flagged, but the rationale has a hole.**
The deviation is reasonable (full delta logs are heavy to persist; metadata carries the retrieve-before-reflect signal). The plan flags it (good, per the "no silent descope" rule). **But:** "retrieve-before-reflect" (R8, the ACE/DC research basis) is specifically about *not* collapsing prior reasoning into lossy summaries — that is the whole point of the incremental-delta design the plan cites (arXiv:2510.04618). Persisting only `CycleMetadata` (counts + `processed_ids` + `time_window`) and *discarding the deltas* reintroduces exactly the context-collapse the deltas were meant to prevent, on the cross-cycle axis. The prior cycle's *decisions* (what was promoted, what was quarantined and why) are the highest-value context for the next cycle's reflection — and those live in `CycleDelta`, not `CycleMetadata`. **Recommend:** persist a *bounded* delta digest (e.g. last cycle's `Quarantine{reason}` + `Promote{provenance}` deltas), not just metadata counts. The "heavy to persist" objection is weak: Task 7 already bounds history to last-8 FIFO; bound the *delta payload* too rather than dropping it. At minimum, acknowledge that metadata-only prior_reports is a *partial* retrieve-before-reflect.

**D3 (produce/apply split for the review gate) — [sound, keep].** The issue's pipeline step 4 ("present patterns for human review before any promotion") genuinely requires that `run` not auto-write. Splitting `run`(produce) from `apply_cycle_report`(commit) is the correct shape and matches the capability-boundary design already in `DreamContext` (`cognitive.rs:21-31`). The only caution: the split widens the non-atomic window (§5) because consolidate (a write, run inside produce) now commits arbitrarily long before apply. That is a §5 problem, not a D3 problem — D3 itself is right.

**D9 (DBSCAN eps vs retention-ratio confusion) — [sound, and the catch is correct].** The plan correctly identifies that `DreamCycleConfig.compression_ratios` (Episodic=0.2/Semantic=0.8/Procedural=0.8) are **retention fractions, not distances** (`types.rs:438-447` confirms: "Fraction of facts to retain per FactType") and must not be fed to DBSCAN `eps`. Fixed `eps=0.15` (cos≥0.85) aligns with `CLUSTER_SIMILARITY_THRESHOLD=0.85` (`cluster.rs:11`, verified). `min_pts=3` is conventional. `1 - cosine_similarity` as distance is NaN-safe because `cosine_similarity` returns 0.0 on a zero vector (`vector.rs:20`, plan line 19 — verified the function exists; `dist = 1-0 = 1`, finite). **However:** the plan then *abandons* `compression_ratios` entirely — the default impl (Task 9) uses per-type P75 importance gating and fixed eps, and never consumes `compression_ratios`. So `DreamCycleConfig.compression_ratios` becomes a **dead config field** in the default impl. That is defensible (it is the consumer's knob, unused by the pure-Rust default) but the plan should say so explicitly, or the field reads as wired-but-ignored. **[LOW]** Note in Task 9 that `compression_ratios` is intentionally unused by `DefaultDreamCycle` (deferred to #578's parametric eps), so a reader doesn't assume a bug.

## 7. Additional findings the plan's scrutiny list did not name

**[HIGH] — `TagOutcome` delta has the *same* self-deadlock trap as `Promote`, and the plan does not flag it.** The plan's "Lock trap" grounding (plan line 17) names *only* `promote_with_lineage` and mandates `promote_in_conn`. But `TagOutcome→EventStore::insert OutcomeSignal` (Task 5) must **not** route through `MemoryEngine::record_outcome` — that method acquires its own write lock: `record_outcome` does `self.write_conn()?` at `outcome.rs:53` (and a separate read at `outcome.rs:32`). Called inside the held `apply_cycle_report` transaction → self-deadlock on the non-reentrant `parking_lot::Mutex` (`connection_pool.rs:19`). Task 5's text *happens* to say "`EventStore::insert`" (the inner helper, `outcome.rs:54`) rather than `record_outcome`, so a literal implementation is safe — but the plan only *documents* the trap for promote and only mandates a `_in_conn` extraction for promote. An implementer wiring `TagOutcome` through the obvious `record_outcome` facade self-deadlocks, and Task 5 test (g) only regression-guards the *Promote* lock path. **Fix:** extend the lock-trap note and the lock-safety regression test (g) to cover `TagOutcome` too; or extract `record_outcome_in_conn(&Connection,...)` symmetric to `promote_in_conn`. Note also `record_outcome` validates fact existence on a *read* connection (`outcome.rs:32`) — inside a write transaction that read goes to a *different* pooled connection that **cannot see the uncommitted savepoint state**, so an outcome tagged on an AddFact'd fact (same id-space problem as §2) would fail existence validation. Use the shared transaction connection for both the existence check and the insert.

**[MEDIUM] — `validate_report` (read conn) → `apply` (write conn) is a TOCTOU.** Task 5 runs `validate_report` on a single *read* connection, then opens a *write* connection for apply. Between them the corpus can change (another writer expires a fact the validator just confirmed exists). `with_read` and `write_conn` are different pooled connections (`engine/mod.rs:492-507`). Under the engine's single-writer model the *only* other writer is... the same thread, so in practice the window is empty *unless* `apply` is called from a different thread than `validate`, or `validate` is exposed as a separate `pub` pre-flight the consumer calls earlier. Since `apply_cycle_report` calls both internally back-to-back, the window is small but nonzero (read pool ≠ write conn, no shared snapshot). **Cleaner:** run `validate_report` on the *same write connection*, inside the transaction, before replaying — then validation and apply see one consistent snapshot and a failed validation rolls back trivially. The plan's "single read connection" for validation is a premature optimization that introduces a correctness seam.

**[LOW] — `expire()` is not idempotent and Quarantine validation must account for it.** `expire()` errors `NotFound` if the row is already expired (`facts.rs:333` guard `t_expired IS NULL`, `:336` returns NotFound on 0 rows changed). Task 5 validates "`Quarantine` not-already-expired" — good — but two `Quarantine` deltas for the same id *within one report*, or a `Quarantine` after a `Supersede`(which also expires), will fail at apply with a `NotFound` masquerading as a missing fact. The validator (read-conn, pre-replay) cannot see intra-report expirations. This is another symptom of the §2/§7 id-and-state-tracking gap: the validator must simulate the report's own mutations (a fact expired by an earlier delta is "already expired" for a later one), not just check initial DB state.
