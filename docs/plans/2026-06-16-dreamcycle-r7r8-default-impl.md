### Honest limitations to surface (not bugs — scope boundaries)

- **The default impl is not fully "LLM-free."** It reuses the existing 3-pass `consolidate()`, which requires an injected `&dyn SummaryGenerator` + `&dyn EmbeddingProvider`. `DefaultDreamCycle` is constructed with both (the consumer's). The DBSCAN clustering + delta emission themselves are pure-Rust deterministic and immune to context collapse; consolidation summaries are extractive in a trivial generator.
- **A full `run_dream_cycle` is not globally atomic.** `consolidate()` commits in its own transaction _before_ `apply_cycle_report`'s savepoint (matching the shipped "consolidate-first" ordering). A single-transaction cycle is **#578**. Recovery: if the process dies between the consolidate commit and apply, the next run re-selects the (still-unmarked) window and re-emits — consolidation is idempotent-ish and no facts were marked dream-cycled, so no work is lost or double-applied.
- **Concurrent double-fire is NOT idempotent.** The watermark + metadata marker make a _sequential_ re-run a near-noop, but two cycles firing at once can both select the same window. Mutual exclusion is **#207 (distributed lock)** / **#209 (skip-if-caller-wrote)** — out of this PR's scope.

### Review-driven design corrections (from the 3-reviewer adversarial pass — see `*-review-*.md` artifacts)

- **`Supersede` is re-wired to a graph edge, NOT lineage.** `lineage` has `UNIQUE(wisdom_fact_id)` + `provenance NOT NULL` (schema.rs:683), so `LineageStore::insert(new ← [old])` collides whenever `new_id` is also a `Promote` target (the expected DBSCAN path) and has no provenance value. `edges.relation_type` is a free `String` (edges.rs), so `Supersede{old,new}` = `expire(old)` + `EdgeStore::insert(NewEdge{ source_fact_id: new, target_fact_id: old, relation_type: "supersedes", … })`. Zero schema cost. (D10.)
- **`apply_cycle_report` is an `impl MemoryEngine` method, not a free fn**, because `TagOutcome` needs `EventStore::new(conn, &self.upcaster_registry)` (events.rs:112) and the HNSW handle. `TagOutcome` inserts the `OutcomeSignal` event **on the shared transaction** — it does NOT call `record_outcome` (which acquires its own `write_conn`, outcome.rs:53 → self-deadlock on the non-reentrant Mutex, same trap as `Promote`).
- **Validation runs on the single held write connection**, not a separate `pool.read()` guard: on in-memory engines (the default test config) `read()` and `write_conn()` contend the same `Mutex<Connection>`, so a two-guard validate→apply can deadlock. One acquisition, validate-then-apply.
